أريد منك تنفيذ Architecture Audit + Refactor شامل لمشروع "تسعيرة" الموجود في هذا المشروع.

IMPORTANT:
لا تبدأ بتعديل الكود مباشرة.
أولًا افحص المشروع بالكامل وافهم الـ architecture الحالية، ثم ضع خطة تنفيذ دقيقة، وبعد موافقتي ابدأ التنفيذ.

المشروع حاليًا يعمل، وفيه Features موجودة بالفعل، لذلك الهدف ليس إعادة بناء المشروع من الصفر أو حذف الخصائص الموجودة، وإنما إعادة تنظيم الـ architecture وتقوية النظام مع الحفاظ على الـ existing functionality.

==================================================
1. المشكلة الأساسية
==================================================

المشروع حاليًا يعاني من مشاكل Architecture واضحة:

1. الـ Admin يتم التعامل معه تقريبًا كمستخدم عادي مع Role إضافي.
2. الـ Client / Employee / Admin يستخدمون نفس الـ Dashboard والمنطق الداخلي بدرجات كبيرة.
3. الـ Role system بسيط جدًا ولا يوجد Permission System حقيقي.
4. توجد Conditional checks كثيرة مثل:
   if ($role === 'admin')
   if ($role === 'client')
   if ($role === 'employee')
   في أماكن كثيرة من المشروع.
5. الـ Admin لا يشعر بأنه System Administrator حقيقي، بل Client/Employee مع صلاحيات إضافية.
6. الـ Dashboard يحتوي على مسؤوليات كثيرة جدًا.
7. بعض ملفات الـ frontend/backend ضخمة ومتشابكة.
8. توجد عمليات Database initialization/index creation/seeding داخل request lifecycle.
9. توجد استعلامات كثيرة ومتكررة تؤثر على الأداء.
10. يوجد ضعف في الـ MongoDB indexing مقارنة بالـ queries المستخدمة.
11. يوجد تداخل بين Client Workspace و Employee Workspace و Admin Management.
12. النظام يفتقد Organization/Tenant architecture واضحة.
13. الـ Role والـ Plan والـ Feature Access متداخلون.
14. إضافة Feature جديدة أصبحت صعبة بسبب الترابط العالي بين الملفات.
15. توجد لخبطة في الـ navigation والـ UX نتيجة محاولة استخدام نفس النظام لكل الأدوار.
16. أريد نظامًا قويًا وقابلًا للتوسع وليس مجرد Dashboard شكله أفضل.

ROLE

6. Organization / Tenant Architecture
==================================================

افحص هل المشروع يحتاج Organization/Tenant layer.

إذا كان مناسبًا، صمم:

Organization
→ Members
→ Roles
→ Permissions
→ Quotes
→ Customers
→ Projects
→ Subscription
→ Settings

بحيث لا يصبح User هو الوحدة الأساسية الوحيدة للنظام.

يجب أن يكون النظام مستعدًا لتعامل شركة واحدة مع عدة موظفين.

لا تنفذ Multi-tenancy بشكل سطحي.
يجب أن يكون organization isolation واضحًا في database queries وauthorization.

==================================================
7. Subscription / Entitlements
==================================================

لا تجعل:

PLAN

هو نفسه:

PERMISSION.

الـ Plan يجب أن يحدد Feature Entitlements / Limits.

مثال:

quotes.max_monthly
team.max_members
pdf.unlimited
advanced_pricing.enabled
priority_support.enabled

بينما الـ Permission يحدد من يستطيع استخدام الـ feature داخل الـ organization.

مثال:

ROLE:
employee

PERMISSION:
quotes.create

PLAN:
PRO

ENTITLEMENT:
advanced_pricing = true

القرار النهائي يجب أن يكون:

Permission + Entitlement + Resource Ownership/Organization Scope

Database Bootstrap / Migration / Setup process

==================================================
10. MongoDB Performance
==================================================

حلل جميع queries المستخدمة فعليًا.

أنشئ Index strategy مبنية على queries الحقيقية.

افحص خصوصًا:

users
quotes
messages
activity_log
subscriptions
projects
clients

ولا تضف indexes عشوائية.

لكل index جديد يجب أن تعرف:

- Query التي يحتاجها
- سبب وجوده
- تأثيره المتوقع
- هل يوجد index مكرر

وأضف:

pagination

حيثما توجد قوائم كبيرة.

تجنب:

findAll بدون limit

أو تحميل آلاف records إلى الذاكرة.

==================================================
11. Dashboard Performance
==================================================

افحص الصفحة الرئيسية والـ Admin Dashboard.

لا أريد عشرات DB queries المتسلسلة عند فتح Dashboard.

صمم summary endpoints مناسبة.

مثال:

GET /api/admin/overview

ويعيد فقط البيانات المطلوبة للـ Admin Overview.

وكذلك:

GET /api/workspace/overview

حسب الحاجة.

استخدم caching أو aggregation عندما يكون مناسبًا.

لا تضف caching بشكل أعمى.

==================================================
16. Admin Security
==================================================

Admin actions يجب أن تكون أكثر صرامة.

أي عملية حساسة مثل:

- تغيير Role
- تغيير Subscription
- تغيير Permissions
- حذف User
- حذف Organization
- تعديل System Settings
- تغيير Billing state

يجب أن:

1. تتحقق من permission
2. تتحقق من resource scope
3. تسجل Audit Log
4. لا تعتمد على client-side state
